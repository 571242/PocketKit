### 3.1 为什么没有引入 OpenCV（父会话已同意）

任务书允许 `org.opencv:opencv:4.12.0`（Maven 官方，Apache-2.0）。本模块未使用，理由：

1. A03 实际需要的三件事（找边、透视校正、去阴影）各自都很小，且**能在无设备环境下用合成图验证**；
   OpenCV 的 native `.so` 无法在本机验证（无硬件加速、无真机）。
2. APK 体积：OpenCV AAR 约 30–40 MB（含各 ABI native 库）。
3. 许可面与审计面更小。
4. 全部像素运算以 `int[] ARGB` 实现于 `ScanCore`，自检 20 项覆盖（见 §4）。

若后续需要更强的边缘检测（例如极低对比度的实拍文档），再评估引入。

### 3.3 GIF：vendored 源码来源、许可与修改说明

父会话决定：**不**把 `com.madgag:animated-gif-lib:1.4` 的 JAR 直接加进 Android 构建
（`AnimatedGifEncoder.java` 与 `GifDecoder.java` 依赖 `java.awt.*` / `java.awt.image.*`，Android 上没有这些类），
而是从**官方 Maven Central 的 source JAR** 中取出不含 AWT 的编码核心，移植为纯 `byte[]`/Android Bitmap 实现，
**不引入 AWT、不使用 JitPack**。

**修改说明**（同时写在两个文件的 source header 里）：

1. 包名 `com.madgag.gif.fmsware` → `cn.xianhua.pocketkit.media.gif`。
2. `LZWEncoder` 由包私有改为 `public`（构造函数与 `encode()` 亦然），因为改由同包的 `GifWriter` 驱动。
3. **算法零改动**：两者本来就不依赖 AWT，直接接收/产出 `byte[]`。

**自行重写、未移植的部分**（上游这两个文件均依赖 AWT，故按规范重写）：

- `.../media/gif/GifWriter.java`：GIF89a 写头、NETSCAPE2.0 循环扩展、图形控制扩展、图像描述符、局部调色板、LZW 调用与结尾 `0x3B`。
  - 每帧**独立量化并写局部调色板**；透明像素写保留索引并**排除在量化样本之外**；disposal 固定为 **2（还原背景）**；延迟下限 20ms。
  - 通道顺序按上游语义处理：`NeuQuant` 的调色板与 `map()` 使用**同一顺序**。上游喂 BGR（源为 `TYPE_3BYTE_BGR`）后再交换 R/B；我方直接喂 RGB，因此**不交换**且以 `map(r,g,b)` 调用。这两者写错其一会让输出整体偏灰或红蓝互换——往返测试专门盯住这一点。
- `.../media/gif/GifReader.java`：完整 GIF89a 解析，**实现**透明索引、disposal 0/1/2/3、局部与全局调色板、交错（四遍行序还原）、逐帧延迟、NETSCAPE2.0 循环次数、LZW 变长码与 KwKwK 情形。

**许可证交付**：`NeuQuant.java` 与 `LZWEncoder.java` 的原始许可文本已随源文件原样保留；
Apache V2 许可证全文与动画 GIF 库的 NOTICE 由**父会话统一打包**（本模块不自行改动许可清单）。

**往返验证**（`.scratch/media/GifRoundTripTest.java`，33 项断言全部通过）：

| 覆盖项 | 断言 |
| --- | --- |
| 不透明多帧 | 帧数、尺寸、三帧颜色各自正确且互不相同（证明不是只抽第一帧） |
| 透明通道 | 透明半边往返后仍透明（未被涂黑），不透明半边颜色正确 |
| 延迟与循环 | 每帧延迟逐一保留；循环 0 = 无限、3 = 三次；过小延迟被抬到下限 |

### 3.2 Google ML Kit 数据披露（必须计入产品文案）

`text-recognition-chinese`、`barcode-scanning`、`face-detection` 为**闭源 SDK**，
官方 data disclosure 说明其可能在运行时收集诊断与性能数据。因此：

- **不得声称本应用"零通信"或"全开源"**。
- 相关界面文案已明示：「识别在本机完成，图片不会上传；该 SDK 为闭源，可能收集诊断与性能数据。」
- 涉及入口：020（识别）、034（OCR）、A04（人脸检测）。
- 界面未做联网开关：识别本身离线可用，但 SDK 的诊断上报不由本应用控制，需在「关于/隐私」页说明。

## 4. 算法自检

**三套自检**：`MediaSelfTest`（279 项：编码/正则/几何/参数/入口合同）、`GifRoundTripTest`
（33 项：GIF 合成与分解往返）、`EnhanceSelfTest`（69 项：锐化/重采样/比例还原/计数/表格结构/人脸对齐与掩膜）。

**运行方式**（不触发 Gradle，因此不会与父会话的整包构建冲突）：

```bash
cd F:/SPACE/PocketKit/.scratch/media && bash check.sh
```

脚本做两件事：用最高版本优先的类路径编译媒体模块（含 `BaseToolActivity`、`MediaToolsActivity`
与只读引用的 `core/SizeFmt.java`、`core/ToolException.java`），然后运行 `MediaSelfTest`。

**当前结果：媒体算法自检 279 项 + GIF 往返自检 33 项 + 增强与结构分析自检 69 项，共 381 项全部通过。**

覆盖内容（均为不依赖设备与 Android 运行时的纯逻辑）：

| 分组 | 覆盖点 |
| --- | --- |
| Wi-Fi 二维码 | 基本负载格式；`; , : " \` 转义与还原；开放网络不写密码字段；隐藏网络 `H:true`；空 SSID / 缺密码被拒；普通网址不误判 |
| 文本脱敏 | 手机号、座机、带 `+` 的邮箱、分组卡号；掩码等长且保留周边文字；长数字串只产生一个区间（重叠合并）；普通中文不误报；开关关闭后不命中 |
| 目标大小搜索 | 二分结果不超目标且尽量接近上限；目标过小时如实标记未达成；缩放不放大原图；按像素缩放不超上限且保持比例；格式判定 |
| 找边与校正 | 深底白纸检出（四角误差 < 12px）；纯色图如实报告"未找到"；整幅同色不谎称找到边；浅底深纸同样检出；透视校正后四角为纸面色、文字行水平；单应矩阵求解 |
| 去阴影 | 背景亮度标准差 30.6 → 0.3；墨迹仍保持深色；强度 0 时像素完全不变 |
| 对比度/二值 | 拉伸扩大动态范围；双峰直方图 Otsu 阈值落在两峰之间 |
| 扫描整条流水线 | 合成"拍歪+带阴影"照片 → 找边 → 校正 → 去阴影 → 二值；断言最终只剩黑白两色、黑像素占比 1%~40%、黑像素集中在少数几行（说明文字已水平） |
| 手动四角 | 百分比解析与像素换算；少于/多于四角、非数字、越界被拒；自交四边形被拒（顺序填错会报错而非产出扭曲图） |
| 旋转裁剪 | 90/270 交换宽高、180 不变；负角度与超一圈归一化；居中比例裁剪的尺寸与居中位置；内缩上限；越界裁剪裁到图片内（不是平移）；零宽与完全界外被拒 |
| 九格 | 9 格面积合计严格等于原图；相邻格无缝无重叠；不能被 3 整除的尺寸也全覆盖 |
| 像素化 | 均匀色取平均后不变；左右黑白图平均后正确；双色量化只产出 0/255 |

## 5. 未验证点与已知限制（如实声明）

### 5.1 全局

- **全部入口未经真机或模拟器验证。** 本机 AVD 无硬件加速（AEHD/HAXM/WHPX 均不可用），
  环境文档已判定模拟器不可作为可靠验证路径。**算法自检不能替代真机验证。**
- 若父会话能接入真机，建议优先验证：034 OCR、A08 压缩、A01 PDF、A03 扫描这四条
  （分别涉及闭源 SDK、硬件编码器、第三方 PDF 库、图像算法，风险最高）。
- 权限：本模块**不需要任何运行时权限**（图像/文档/视频全部走 SAF 自授权）。相机相关功能未实现，故未申请 CAMERA。

### 5.4 会上传数据的两个入口（010 / 022）

这是全模块唯一会把文件发到外部服务器的功能，防护不是可选项：

1. **逐次确认弹窗**：每次上传前弹出对话框，写明服务名（0x0.st / catbox.moe）、运营方所在地、
   具体发送什么（图片内容 + User-Agent；0x0.st 另记录 IP）、以及后果（公开链接、第三方保留、
   本应用无法删除）。只有点「同意并上传」才发请求。
2. **仅 HTTPS**：`Uploader.requireHttps()` 拒绝明文地址，否则文件会在传输中可读。
3. **文件名防穿越**：上传前对文件名做净化（见 `sanitizeName`，自检覆盖 `etc/passwd`、`..\`、
   换行等输入）。
4. **结果校验**：图床返回必须是 http(s) 链接才认作成功；HTML 错误页会被判为失败，不会把
   一段错误信息当链接展示。
5. **022 的默认方式不上传**：默认走系统分享面板交给用户自己选择的应用（如 Google Lens）。

服务端点取自运营方公开文档：0x0.st 的 `POST https://0x0.st`（字段 `file`，另有 `secret` 与
`expires`）与 catbox.moe 的 `POST https://catbox.moe/user/api.php`（`reqtype=fileupload`、
`fileToUpload`）。**本工具不抓取也不显示搜索结果**：Yandex / Bing 只用于"按链接打开搜索页"，
由其自己展示结果；Google Lens 与 TinEye 的按链接入口依赖浏览器会话，构造 URL 不可靠，故不提供。

### 5.5 采样标志必须显式映射（A08 / 080）

`MediaExtractor` 与 `MediaCodec` 各有一套看起来相似、**数值并不通用**的标志位。实测（`FlagTypes` 探针）：

| Extractor 标志 | 值 | 同名 Codec 标志 | 值 | 后果 |
| --- | --- | --- | --- | --- |
| `SAMPLE_FLAG_SYNC` | 1 | `BUFFER_FLAG_KEY_FRAME` | 1 | 恰好一致，容易被误认为可以直传 |
| `SAMPLE_FLAG_ENCRYPTED` | 2 | `BUFFER_FLAG_CODEC_CONFIG` | 2 | **撞车**：加密采样会被写成编解码器配置 |
| `SAMPLE_FLAG_PARTIAL_FRAME` | 4 | `BUFFER_FLAG_END_OF_STREAM` | 4 | **撞车**：分段帧会被写成流结束，直接截断输出 |

因此**不能**把 `getSampleFlags()` 的值直接赋给 `BufferInfo.flags`。全部四处调用点改为经过
`SampleFlags` 显式映射（`VideoTool` 第 304/368/528/578 行）：

- `SYNC` → `BUFFER_FLAG_KEY_FRAME`（数值相同也照样显式写，避免"碰巧对"）。
- `PARTIAL_FRAME` → 送**解码器**时映射为 `BUFFER_FLAG_PARTIAL_FRAME`；送**重封装**时
  **明确拒绝**并说明原因（muxer 无法重组被拆开的帧，写出去就是损坏文件）。
- `ENCRYPTED` → 两个方向都**明确拒绝**并给出可操作说明（需要 MediaCrypto 才能解码，也无法复制进
  新容器）。不静默产出错误标志污染输出，也不靠 `@SuppressLint` 掩盖。

自检 `FlagsSelfTest`（37 项）把上表的数值、两条撞车关系、四条映射规则、拒绝文案与
"映射结果只含合法位"全部固定下来，避免了"碰巧正确"。

### 5.6 OCR 预览与完整结果分离

034 原先把**完整**识别文本拼进结果面板，却又声称"以上为前 4000 字预览"——自相矛盾，且长文档会
让界面卡顿。现在预览**真的**截断到 4000 字符（按码点截断，不会把 emoji 或罕用汉字切成半个），
同时完整文本单独保留给 TXT 导出；提示语给出实际字符数。

### 5.4 下一步的具体来源（不留空话）

## 6. 设计与实现约定（给后续维护者）

1. **不覆盖用户文件。** 结果一律先写应用 cache，再经 `ACTION_CREATE_DOCUMENT` 由用户选定位置；
   重名冲突交给系统的覆盖确认，不自行猜测。输入只经由用户选择的 URI 读取，不扫描磁盘。
2. **取消是协作式的。** 长循环每步调 `Cancel.check()`；取消时抛出 `Cancel.Stop`，已写出的临时文件被删除，
   目标文件从未被打开，因此不存在"半个文件"。
3. **内存有上限。** `ImageIo.DEFAULT_MAX_PIXELS`（800 万像素）是默认预算；超过则降采样，
   需要精确尺寸的场合传 `strictSize=true` 直接报错而不是悄悄给一张更小的图。
4. **推测与事实分开。** 界面文案区分"实测值"（如编码后文件大小）与"估计值"（如体积预估）。
5. **失败要说清原因与下一步。** 错误信息说明发生了什么、怎么改，不道歉、不含糊。
6. **不谎称能力。** `supports()` 只对真实现返回 true；算法未验证就写"未在真机验证"；
   找不到可信模型就保持 false 并写明依赖缺口。
